# 软件架构设计规范

## 1. 目的与边界

本文定义 Atha 设计、变更和评审软件架构时的共同方法。它回答“为什么设计、由什么驱动、如何选择和验证”，不替代产品事实、当前架构、代码地图或具体变更记录，也不是对现有实现的审计结论。是否重构或重写，必须由驱动因素、风险和证据决定，不能由模式偏好决定。

本规范综合两本原书的方法，并把它们适配为 Atha 的最小治理规则：

- **必须**：不满足即不能通过架构评审；例外必须在已接受的 change 或 ADR 中写明影响、风险、证据、回滚和复查条件。
- **应该**：默认遵守；偏离时必须记录理由。
- **可以**：只在实际驱动因素证明有价值时采用，不为未来预留空抽象。
- **书中综合**：来自两书，可用于一般软件系统。
- **Atha 适配**：结合本项目约束形成的项目规则，不声称是原书原句或唯一实现。
- **当前事实**：按 `CONTEXT.md` 的事实所有权表定位唯一所有者，并以真实代码和检查核对；本文不另立所有者清单。

## 3. 架构的定义与总原则

软件架构是为了推理系统而需要的一组结构；结构由软件元素、元素间关系及其属性组成。至少要区分模块结构、运行时组件与连接器结构，以及软件到硬件、文件系统、进程或团队的分配结构。一个目录树、一张框图或技术清单都不能单独代表完整架构。[SAIP4，第 1 章 §1.1-1.2；DSA2，第 1 章 §1.2，PDF 第 19-23 页]

架构没有脱离目的的“好”或“坏”，只有对明确目标更适合或更不适合。架构决策是对驱动因素产生重要、非局部后果的决策；它们往往较早、影响广且修改昂贵。[SAIP4，第 1 章 §1.3、第 2 章；DSA2，第 2 章 §2.2-2.4，PDF 第 29-43 页]

所有架构工作必须遵守以下原则：

1. **目的优先**：先写清本轮设计目的，再谈技术或模式。
2. **质量属性可测**：不得把“快、安全、可扩展、易维护”当作完整需求；必须落成场景和响应度量。
3. **风险驱动**：优先处理业务重要性高且技术风险高的驱动因素；设计到“足以降低当前风险”为止。
4. **高内聚、低耦合**：把共同变化的责任放在一起，经稳定、窄小的接口隔离可能变化的实现。
5. **信息隐藏与关注点分离**：边界按变化、责任和信任划分，不按框架目录或组织习惯机械分层。
6. **最少结构**：只设计和维护能支持构建、分析或教育的结构与视图；小系统不需要齐全的图册。[SAIP4，第 1 章 §1.2“Fewer Is Better”]
7. **复用已有知识**：优先选择已验证的战术、模式、标准和现有项目能力；模式必须针对场景实例化，不能按名称套用。
8. **简单一致**：交互方式、错误语义和命名保持少而一致；每新增一种机制都必须说明收益和运维成本。
9. **证据而非偏好**：事实优先；假设显式；未知或高风险处用最小原型、分析或真实测量消除不确定性。
10. **设计、记录、分析同步**：重要决策做出时就记录并分析，不能把文档和评估推迟到实现结束。
11. **增量演进**：架构随产品增量共同生长；先贯通最重要路径，反复验证，不一次性预建未来平台。
12. **边界可执行**：能由类型、可见性、数据库约束、测试、lint 或构建检查强制的规则，不只写在图里。

这些原则综合自 SAIP4 第 1-3、15、20-24 章，以及 DSA2 第 2-4、10-12 章；其中“最少结构”和“不预建未来平台”是结合 Atha 早期阶段的收敛性适配。

## 4. 架构驱动因素

每一轮架构设计必须有一个驱动因素清单。DSA2 将输入归纳为设计目的、主要功能、质量属性、架构关注点和约束；SAIP4 进一步要求把高影响且高业务价值的需求识别为架构显著需求（ASR）。[SAIP4，第 19 章；DSA2，第 2 章 §2.4，PDF 第 34-43 页]

| 输入 | 必须回答的问题 | 最小产物 |
| --- | --- | --- |
| 设计目的 | 本轮为了估算、原型、首个可用切片、演进还是风险消除？何时停止？ | 一句话目的和退出条件 |
| 业务或使命目标 | 哪个用户或项目结果最重要？失败代价是什么？ | 已排序目标、利益相关者和成功信号 |
| 主要功能 | 哪些少数端到端用例决定责任分配或跨越多个边界？ | 主要用例及责任流 |
| 质量属性场景 | 在什么刺激和环境下，系统必须怎样响应，达到什么数值？ | 场景、优先级和证据计划 |
| 架构关注点 | 日志、错误、配置、依赖、迁移、隐私、构建、运维等隐含问题是什么？ | 关注点或由其派生的场景 |
| 约束 | 哪些技术、法律、兼容、团队、预算或期限条件无法自由改变？ | 约束、来源、有效期和可否协商 |
| 既有系统 | 当前真实结构、接口、数据和债务是什么？ | 以代码和测试核对的 as-built 基线 |

驱动因素必须进入同一个架构 backlog，并以“业务重要性 × 技术风险”的粗粒度等级排序。最高优先级项先设计、验证和关闭；低优先级项不得借“以后可能需要”引入当前复杂度。[SAIP4，第 19 章 §19.4、第 20 章 §20.2、§20.6；DSA2，第 2 章 §2.4.2，PDF 第 35-40 页]

## 5. 质量属性场景

每个重要质量属性必须用六部分场景表达：[SAIP4，第 3 章 §3.3；DSA2，第 2 章 §2.4.2，PDF 第 35-40 页]

| 字段 | 含义 |
| --- | --- |
| 刺激源 | 谁或什么产生事件 |
| 刺激 | 发生了什么 |
| 环境 | 正常、峰值、离线、降级、升级、崩溃或攻击等条件 |
| 制品 | 受影响的系统、数据、模块或接口 |
| 响应 | 系统采取什么可观察行为 |
| 响应度量 | 延迟、吞吐、错误率、恢复时间、改动范围、数据损失、资源上限等可判定标准 |

场景还应该记录 ID、关联目标、业务重要性、技术风险、负责人、验证层级和证据位置。度量未知时，应该先给出可接受范围或数量级并标成待验证假设，不能退回形容词。标准质量属性清单只用于防漏；Atha 可以定义“引用保真”等领域质量，但仍必须先收集场景、建立影响模型，再选择设计手段。[SAIP4，第 14 章 §14.2-14.3]

## 6. 迭代设计流程

架构设计采用精简的 Attribute-Driven Design（ADD）循环。每轮可以包含多个迭代，每个迭代只聚焦一组相关驱动因素。[SAIP4，第 20 章；DSA2，第 4 章 §4.2，PDF 第 77-104 页]

| 步骤 | 必须完成的动作 | 退出证据 |
| --- | --- | --- |
| 1. 复核输入 | 核对目的、主要功能、优先场景、约束、关注点和现状；纠正遗漏或过期输入 | 已排序 backlog 和本轮目的 |
| 2. 设定迭代目标 | 选择本次要降低的最高风险，声明成功条件 | 场景 ID、风险和停止条件 |
| 3. 选择细化对象 | 选系统、模块、运行时组件、数据或接口；棕地设计先核对真实实现 | 对象、现状和责任边界 |
| 4. 产生并选择方案 | 至少比较当前方案与一个合理替代；按驱动因素、约束、成本和风险选择战术、模式或现有组件 | 方案比较、假设和证据需求 |
| 5. 实例化结构 | 明确元素、责任、关系、属性和接口；模式名不能代替这些决定 | 视图草图、责任表和接口契约 |
| 6. 记录决策 | 当场记录决策、理由、被弃方案、权衡、未知和位置 | 更新的 change 或 ADR |
| 7. 分析与复核 | 用场景走查、问卷、模型、原型或实测判断目标是否满足，并检查对其他质量的副作用 | 风险、非风险、敏感点、权衡点和结论 |

若关键风险未降到可接受水平，则重复步骤 2-7；若剩余项价值低于设计成本，则停止并保留 backlog。完成是针对某一设计轮次和目的的“足够好”，不是架构永久冻结。[SAIP4，第 20 章 §20.6；DSA2，第 4 章 §4.8，PDF 第 102-104 页]

当技术新颖、团队无经验、质量目标存在明显不确定性、配置或集成行为未知且没有可信证据时，应该做最小的抛弃式原型。原型必须写明假设、测量和停止条件；为快速验证而牺牲的结构不能未经重新设计直接成为产品基线。[SAIP4，第 20 章 §20.3；DSA2，第 4 章 §4.4，PDF 第 87-91 页]

## 7. 决策与接口标准

### 7.1 九项决策检查

每个重要架构决策必须依次检查以下问题：[DSA2，第 3 章 §3.1，PDF 第 46-49 页]

1. 有哪些事实和可复核证据？
2. 做了哪些显式或隐式假设，如何验证？
3. 团队、预算、法规、用户和既有决定等上下文是什么？
4. 最坏结果、概率和影响是什么？
5. 哪些目标优先，放弃什么？
6. 决策在哪个时间范围内成立，何时复查？
7. 除首个想法外，还有哪些实际可行的方案？
8. 哪些约束限制选择，能否协商或绕开？
9. 各方案对成本、质量属性和利益相关者的利弊是什么？

两个方案后果近似时，应该选择更简单、可逆且项目已有能力支持的方案并继续，不为证明“最优”无限分析。[SAIP4，第 21 章 §21.2]

外部组件或依赖的选择还必须检查：实际解决的问题、总成本、精确 SPDX 与预期分发方式的兼容性、供应商锁定、学习曲线、社区或厂商支持、更新与安全响应、离线可用性、数据与隐私影响，并按适用性履行版权 / 修改说明、署名 / NOTICE、源码提供或重新链接义务。技术名称或“同属 GPL / AGPL”不是理由。[DSA2，第 3 章 §3.2.4，PDF 第 54-55 页；许可与后四项为 Atha 风险适配]

### 7.2 接口契约

跨模块、进程、信任边界或持久化边界的接口必须说明：

- 使用者和权限范围，以及提供和需要的资源；
- 操作、事件和属性的语法与语义；
- 同步或异步、控制流、数据格式、单位、不变量和状态变化；
- 原子性、幂等性、顺序、超时、取消和资源预算（适用时）；
- 输入校验、错误分类、调用者可见结果和恢复责任；
- 版本、兼容、弃用、迁移和回滚策略；
- 安全、隐私及不泄露内容的诊断信号；
- 契约测试或其他可执行约束的位置。

接口应该遵循最少惊讶、小接口、一致访问和不重复原则，不泄露实现细节。公开资源意味着长期维护承诺；调用者依赖未记录的可观察行为，风险由调用者承担。[SAIP4，第 15 章 §15.1-15.3]

## 8. 质量战术与模式

战术是影响单个质量属性响应的基本设计决定；模式是在特定上下文中组合多项战术、平衡多种力量的复用方案。必须先有场景，再选战术，最后才决定是否需要某个模式或技术实现。[SAIP4，第 3 章 §3.4-3.6；DSA2，第 3 章 §3.2，PDF 第 49-55 页]

| 质量属性 | 优先检查的战术方向 | 主要代价或反作用 | 来源 |
| --- | --- | --- | --- |
| 可用性（Availability）与恢复 | 检测故障、从故障恢复、预防故障；事务、回滚、重试、降级 | 状态复杂度、资源成本；重试要求幂等和上限 | SAIP4 第 4 章；DSA2 PDF 第 58-63 页 |
| 可部署性 | 管理部署流水线和已部署系统；可重复构建、替换、回滚 | 兼容窗口、基础设施和测试成本 | SAIP4 第 5 章；DSA2 第 6 章，PDF 第 130-147 页 |
| 资源与能效 | 监控资源、合理分配、减少需求 | 监控开销、降级体验 | SAIP4 第 6 章 |
| 可集成性 | 限制依赖、适配差异、协调交互；遵循标准、使用中介 | 中介增加延迟和维护面 | SAIP4 第 7 章；DSA2 PDF 第 70-73 页 |
| 可修改性 | 提高内聚、降低耦合、在有变更场景时延迟绑定 | 额外抽象和间接层可能降低性能与可读性 | SAIP4 第 8 章；DSA2 PDF 第 63-66 页 |
| 性能 | 控制需求、管理资源；限流、并发、缓存、调度、索引 | 一致性、内存、竞争和复杂度 | SAIP4 第 9 章；DSA2 PDF 第 56-58 页 |
| 安全性（Safety） | 避免进入不安全状态，检测事故并限制或修复损害 | 冗余、保护逻辑及误触发成本 | SAIP4 第 10 章 |
| 安全与隐私 | 检测、抵抗、响应、恢复；最小访问面、隔离、校验、审计 | 可用性、性能和运维成本 | SAIP4 第 11 章；DSA2 PDF 第 66-70 页 |
| 可测试性 | 控制和观察状态、限制复杂度、隔离依赖 | 测试接口不得扩大生产攻击面 | SAIP4 第 12 章 |
| 易用性（Usability） | 支持用户主动控制和系统反馈；取消、撤销、进度和状态模型 | 状态保存和交互复杂度 | SAIP4 第 13 章 |
| 自定义领域质量 | 收集场景、建立参数模型、枚举能影响参数的机制 | 名称争论替代不了度量 | SAIP4 第 14 章 §14.3 |

常用模式只作为候选，不是项目目标：

| 模式 | 适用价值 | 典型代价 | Atha 默认 |
| --- | --- | --- | --- |
| 分层 + 模块化单体 | 单一部署下隔离责任和依赖，避免分布式事务 | 层级过多会增加间接性；单元整体部署和伸缩 | **默认候选**：先保持单桌面部署单元和清晰模块边界 [SAIP4 第 8 章；DSA2 第 3 章 §3.5、PDF 第 63-66 页及第 6 章 §6.2.2、PDF 第 138-140 页] |
| Adapter、Facade、Gateway | 在真实外部、平台或信任边界转换并收窄接口 | 额外跳转可能变成瓶颈或万能层 | 只放在 WebView、平台、文件和存储等真实边界 [DSA2 PDF 第 70-73 页；SAIP4 第 15 章] |
| Strategy、依赖注入 | 已存在替代算法或需要可控测试缝时延迟绑定 | 为单一实现增加抽象和配置 | 第二个真实实现、校准项或测试隔离出现后再用 [SAIP4 第 12 章；DSA2 PDF 第 65-66 页] |
| Publish-Subscribe | 生产者和多个消费者需要独立演进或异步处理 | 顺序、重复、背压、恢复和可观测性复杂 | 直接调用不够时才用；不得再造第二套事实 [SAIP4 第 8 章] |
| Plug-in / Microkernel | 已批准的运行时扩展与多实现生态 | 扩大信任面、版本矩阵和支持成本 | 当前不预建；先要可测的变化场景和安全模型 [SAIP4 第 8 章] |
| MVC、Observer、Memento | 分离交互状态、通知和撤销能力 | 多套状态源会失配 | 只在具体 UI 场景中使用，不复制领域事实 [SAIP4 第 13 章] |
| 冗余、负载均衡、Circuit Breaker | 分布式高可用、容量和级联故障隔离 | 资源、网络、状态和运维复杂度 | 本地单用户产品默认不需要 [SAIP4 第 4、9 章；DSA2 PDF 第 56-63 页] |
| 服务、微服务、动态发现 | 独立部署、独立伸缩或独立团队所有权 | 网络故障、事务、发现、配置、监控和安全 | 没有独立部署或伸缩场景时禁止采用 [SAIP4 第 5、7、17 章；DSA2 第 6 章 §6.2.2，PDF 第 138-140 页] |
| CQRS | 读写负载、模型或一致性要求显著不同 | 双模型、事件和最终一致性复杂度 | 只有度量证明读写分离收益时采用 [DSA2 第 7 章 §7.3.3.2，PDF 第 162-164 页] |

## 9. 文档与决策记录

文档必须服务明确受众和用途：构建、分析或教育。每个视图都要有元素、关系、关键属性、图例和事实来源；视图成本超过收益时可以省略。[SAIP4，第 22 章 §22.1-22.3；DSA2，第 4 章 §4.7，PDF 第 98-102 页]

Atha 的最小架构描述应该从下列集合按风险选择，不要求每次全部新建：

1. **系统上下文**：范围、外部参与者、外部系统、信任边界和主要数据流。
2. **模块视图**：模块责任、允许依赖、数据所有权和对应源码。
3. **运行时视图**：进程、线程、WebView、IPC、连接器、时序、错误和超时。
4. **分配视图**：软件到进程、文件系统、SQLite、平台和团队的映射；若显然简单，一段文字足够。
5. **质量视图**：只为贯穿多个结构的高风险质量建立，例如内容安全、引用保真、数据恢复或性能预算。
6. **接口与数据契约**：跨边界 DTO、协议、schema、迁移、兼容和错误语义。
7. **视图映射与追踪**：模块到运行时、运行时到部署，以及驱动因素到决策、代码和检查的对应关系。

正式图可以使用任意清晰记法；非标准符号必须有图例。结构之外还必须记录行为、上下文、模式实例、变体、术语和重要理由。[SAIP4，第 22 章 §22.4-22.9]

### 9.1 ADR 使用规则（Atha 适配）

新增依赖或技术、长期跨模块边界、公开或持久化接口、schema 与迁移、信任边界、运行拓扑、不可轻易回滚的约束，或者对高优先级场景有显著权衡的决定，必须进入 ADR。局部、可逆、没有非局部后果的实现选择不建 ADR。

ADR 最少包含：状态与日期、上下文、关联驱动因素或场景 ID、决定与范围、候选方案、理由和证据、正负后果、假设、风险及缓解、实施与检查位置、回滚或替代方式、复查触发器、取代关系。ADR 是 Atha 对两书“记录决定、理由、假设、被弃方案和风险”的本地载体；两书并未规定 ADR 文件格式。[SAIP4，第 22 章 §22.7；DSA2，第 4 章 §4.7.2，PDF 第 101-102 页]

## 10. 分析、治理与完成定义

重要设计决策必须分析，分析强度与失败影响和不确定性成比例。优先采用成本最低但能区分风险的方法：经验类比或估算、反思问题、战术问卷、场景走查、模型、模拟、抛弃式原型、实现实验、真实目标测量。证据越接近真实系统，通常成本和置信度越高。[DSA2，第 11 章 §11.3，PDF 第 260-267 页]

每个 change 至少进行一次轻量同行评审：复核目标和架构、更新质量树、按最高优先级场景走查设计、记录风险、非风险、敏感点和权衡点。完整 ATAM 只在影响或投入足以承担外部、多利益相关者评估时使用。[SAIP4，第 21 章 §21.5-21.6；DSA2，第 11 章 §11.6，PDF 第 264-267 页]

架构设计轮次只有同时满足下列条件才能标为完成：

- [ ] 目的、范围、利益相关者、约束和最高优先级驱动因素已确认；
- [ ] 最高优先级质量属性均有六部分场景和响应度量；
- [ ] 每个最高优先级驱动因素可追踪到决定、元素、接口及证据；
- [ ] 关键模式已实例化为具体责任、关系和属性，而非只写模式名；
- [ ] 相关视图与真实代码、数据和运行拓扑一致；
- [ ] 重要决定的替代方案、假设、权衡、风险和复查触发器已记录；
- [ ] 信任边界、失败路径、迁移、恢复、回滚和隐私已按适用性检查；
- [ ] 分析、原型或测试证明响应度量，或风险被有权者明确接受；
- [ ] 剩余未知和债务有负责人、优先级及触发条件，不伪装成“以后再说”；
- [ ] 同行评审的阻塞项已关闭。

架构债务通常表现为职责混杂、复制后分叉、依赖纠缠、循环依赖、失稳接口、设计与实现分离，以及功能速度下降和变更热点。应该从版本历史、问题记录、代码依赖和测试结果寻找证据，并以可量化业务影响决定是否重构；不以“代码不够漂亮”单独发起重写。[SAIP4，第 23 章；DSA2，第 10 章，PDF 第 244-252 页]

## 11. Atha 适配

### 11.1 事实接入规则

项目事实的唯一所有者及路径由 `CONTEXT.md` 的事实所有权表维护，本文不摘录第二份清单。每次架构评审必须先读取 `docs/ACTIVE.md` 指定的 Context Bundle，再按所有权表补充与本次范围直接相关的事实所有者；将核对后的事实转为驱动因素、约束或质量场景，并保留来源链接。

如果本文中的项目示例与事实所有者或真实实现不一致，以事实所有者和真实实现为准，并修正示例。规范性设计规则本身的变化仍必须通过已接受的 change。

### 11.2 默认架构姿态（Atha 适配）

| 主题 | 当前默认 | 只有出现以下证据才升级 |
| --- | --- | --- |
| 部署 | 模块化单体、单桌面产品、清晰分层 | 独立部署、独立伸缩、故障隔离或团队所有权场景 |
| 抽象 | 复用现有具体模块；只在真实边界使用窄接口 | 第二个实现、校准需求、信任隔离或可测试性场景 |
| 扩展 | 不预建插件、远程 API、同步、云端或第二渲染器 | 已接受的产品需求、质量场景和安全模型 |
| 数据 | 单一事实源、显式事务和迁移；缓存与索引可重建 | 事实所有权或负载度量证明需要拆分 |
| 交互 | 进程内直接调用和现有 IPC 优先 | 已证明的异步解耦、耐久投递或背压需求 |
| 技术 | 标准库、平台能力和既有依赖优先 | 当前能力无法满足已量化的驱动因素 |
| 文档 | 更新现有事实所有者和最少相关视图 | 新的长期事实确实没有合适所有者 |

### 11.3 Atha 质量场景基线

下表是评审起点，不替代 change 中的精确环境、样本和数值：

| ID | 场景摘要 | 最低可判定响应 |
| --- | --- | --- |
| A-SEC-01 | 不可信书籍在导入或呈现时包含脚本、外部 URL、越界路径或未知资源 | 拒绝或安全中和；脚本执行、外部请求和路径逃逸均为零；错误不泄露内容 |
| A-REF-01 | 用户从历史 Message 返回已移动、重开或版本变化的书籍 | 校验 Edition 和原文身份；唯一匹配才更新当前位置；历史 Snapshot 不变；歧义不静默误锚 |
| A-DATA-01 | 写入、迁移、导出或导入期间进程异常终止 | 已提交事实完整、未提交事实不可见、约束与完整性检查通过、失败不留下伪成功制品 |
| A-PRIV-01 | 阅读、搜索、消息或 AI 边界发生错误并生成诊断 | 日志可定位稳定阶段和错误码，但不含书名、原始路径、原文、笔记、查询词或提示词 |
| A-PERF-01 | 固定困难样本在支持的 Windows 目标执行打开、翻页、重排或搜索 | 正式 runner 的 P95 和资源使用低于 change 约定门槛；本文不复制易过期数值 |
| A-EVOL-01 | 替换产品界面细节或增加受支持书源能力 | 变化局限于负责的模块和适配边界，不改写 Message、SourceAnchor、SourceSnapshot 的稳定语义 |

这些场景是依据 SAIP4 的六部分场景和自定义质量方法，对 Atha 既定事实作出的项目化推导；正式评审必须补齐刺激源、环境、制品、精确度量和证据层级。

### 11.4 Atha 架构审查清单

**驱动因素**

- [ ] 变更解决当前真实问题，而不是预留假想平台；
- [ ] 设计目的、边界、非目标和停止条件明确；
- [ ] 主要功能、利益相关者、约束和关注点完整；
- [ ] 高业务价值、高技术风险的场景已优先；
- [ ] 新假设有验证方式和失效触发器。

**边界与数据**

- [ ] UI、阅读内核、应用服务、可移植核心、数据和平台责任没有倒置；
- [ ] 平台类型、WebView 对象和 UI 状态没有穿透可移植核心；
- [ ] 书籍输入在进入可信边界前完成限长、规范化、类型和资源校验；
- [ ] 每份事实只有一个所有者，派生索引、缓存和投影可重建；
- [ ] 事务、并发、崩溃一致性、迁移、导出和恢复语义明确；
- [ ] SourceAnchor 当前导航与 SourceSnapshot 历史呈现没有混为一体；
- [ ] 诊断和遥测不收集阅读隐私内容。

**结构与接口**

- [ ] 新模块有单一清楚责任，变化原因相近，允许依赖方向明确；
- [ ] 没有为单一实现创建接口、工厂、注册表或配置系统；
- [ ] 新间接层对应真实变化、信任、测试或集成边界；
- [ ] 接口覆盖错误、超时、取消、幂等、版本和兼容语义；
- [ ] 没有通过共享数据库、全局状态或后门调用绕过模块契约；
- [ ] 没有在缺少独立部署或伸缩场景时引入分布式系统；
- [ ] 性能热路径没有因层次、复制状态或无证据通用化而变长。

**选择与证据**

- [ ] 复用了仓库、标准库、平台或既有依赖中已存在的能力；
- [ ] 至少比较了当前方案和一个合理替代，写明弃用理由；
- [ ] 新依赖已核对精确 SPDX、预期分发兼容性、维护、安全、锁定、体积、离线影响及适用的署名 / NOTICE、源码、修改说明或重新链接义务；
- [ ] 缓存说明失效策略，重试说明幂等和上限，异步说明顺序、重复、背压和恢复；
- [ ] 不确定或高风险决定有最小原型、分析或真实测量；
- [ ] 证据明确区分静态、本地、真实目标和生产等价层级。

**文档与治理**

- [ ] 相关上下文、模块、运行时、数据或质量视图已更新，未新建重复事实；
- [ ] 架构决定与场景、代码和检查双向可追踪；
- [ ] 需要 ADR 的长期决定已记录复查和回滚条件；
- [ ] as-designed 与 as-built 已由代码和正式入口核对；
- [ ] 同行评审记录风险、非风险、敏感点和权衡点；
- [ ] 未验证项、接受的风险和有意债务清楚可见；
- [ ] 没有仅因项目早期、重写便宜就重写；重写必须比增量修复更好地满足已排序驱动因素。

## 12. 典型反模式

- **方案先于问题**：先决定微服务、事件总线、插件、云或框架，再寻找理由；
- **质量形容词**：只写“高性能、可靠、安全、可扩展”，没有刺激、环境和度量；
- **图即架构**：只有框线，没有责任、接口、属性、行为、理由和源码映射；
- **抽象税**：单实现接口、万能 manager、提前配置、为未知格式建工厂；
- **边界泄漏**：UI、平台、数据库或外部格式成为核心领域类型；
- **分布式单体**：服务必须同步联动发布、共享数据或跨服务事务，却承担全部网络复杂度；
- **状态复制**：前端、后端、缓存和索引分别维护互相竞争的事实；
- **快乐路径设计**：忽略错误、取消、超时、降级、迁移、恢复、攻击和隐私；
- **无界重试或缓存**：没有幂等、上限、退避、失效、容量或一致性模型；
- **文档在以后**：理由和假设丢失，设计与实现逐渐分叉；
- **原型升格**：抛弃式原型未经质量和边界重建直接进入产品；
- **隐藏债务**：捷径没有影响、负责人、偿还触发器和业务理由；
- **把早期当作重写理由**：推倒成本低不等于收益高，仍需场景、替代方案和验证。

反模式综合自 SAIP4 第 1、15、20-23 章与 DSA2 第 3、4、10、11 章；其中针对 Atha 的“抽象税、状态复制、早期重写”是项目化风险提示。
