# 微信读书阅读界面与 Atha 自定义分层研究

## 结论

微信读书最值得学习的不是五个底栏按钮，而是阅读页的状态管理：默认只显示正文；用户主动唤出后，控制层才在原页上出现；每次只展开一个局部面板；当前状态就在操作处反馈。Atha 应把这套哲学再推进一步：让高频阅读动作占据第一控制层，把低频排版设置移出底栏，并用渐进披露容纳少数用户的深度定制。

推荐把自定义分成三个内部层级，但不让用户选择“自己属于哪一层”：

- Level 0 是产品默认态，不显示任何级别或设置入口提示；
- Level 1 由用户主动进入“阅读偏好”，只提供少量有明显阅读收益的选项；
- Level 2 藏在“高级”中的每书 CSS 覆盖层，作为完整逃生舱。

暂不开放 JavaScript。CSS 已覆盖当前明确需求；直接执行用户脚本会改变 Atha 现有的安全、性能和可复现渲染边界。只有出现 CSS 无法解决的真实用例时，才另行研究带权限、隔离和安全恢复的用户脚本能力。

本研究只提供 R3“排版与阅读偏好”的产品输入，不批准或实施界面变更。

## 微信读书做对了什么

### 阅读是唯一主界面

沉浸态只有章节名、正文和页码，应用导航、社交和设置全部消失。正文占据完整视觉层级，蓝色只用于可操作链接，其他元素退为低对比灰。用户不需要先“进入专注模式”，打开书后已经处于专注状态。来源：S1。

### 控件临时出现，不把用户带离正文

控制层从原阅读页上浮现，正文仍是空间和上下文背景；目录、进度和排版变化也都在阅读页上即时呈现。用户完成操作后可以直接回到同一段正文，不需要在设置页与书之间来回切换。来源：S2、S3、S5 至 S9。

### 一次只展开一个局部问题

目录、笔记、进度、主题和排版分别使用独立面板；排版内的“首行缩进”和“翻页方式”继续下钻，而不是把所有开关一次铺满。当前选项始终用唯一蓝色强调，状态识别成本低。来源：S3 至 S9。

### 状态与动作贴在一起

目录直接突出“当前读到”，进度面板同时显示百分比和位置滑杆，排版设置在正文上方即时预览。用户不用记住刚才改了什么，也不需要额外的“应用”步骤。来源：S3、S5 至 S9。

## 不应照搬的部分

微信读书的第一控制层已经混入不同频率和不同目标的能力：目录、笔记、进度是阅读过程动作，主题和字体更像一次设置后长期不动的偏好；顶部的付费、社交、分享、更多以及正文上的 AI、听书悬浮按钮又进一步争夺注意力。来源：S2。

目录中的“AI 大纲”把并非阅读成立前提的能力放进最基础的导航入口；笔记页又同时承载热门划线、阅读统计、连接纸书、图片模式、搜索和导出，逐渐变成功能货架。来源：S3、S4。

Atha 不应复制这些入口：

- 删除常驻 AI、听书、社交、付费和分享按钮；未来 AI 只在用户选中文本或明确召唤时出现；
- 目录只拥有目录、当前位置、书签和必要的书内搜索，不加入 AI 大纲；
- 阅读统计、自动翻页、笔记导出等低频能力不进入第一控制层；
- 字体和样式功能保留，但从每次唤出的底栏移到低频“阅读偏好”。

## Atha 的第一控制层

Atha 可以比微信读书少一层心智负担：默认阅读页不常驻按钮；点击正文中部、移动指针到控制区域或使用键盘命令时，才显示临时控制层。第一层只保留三个有明确阅读目的的入口：

1. **目录**：同时显示当前章节，面板内提供当前位置、书签和书内搜索；
2. **进度**：显示当前位置并允许快速跳转，不默认展示时长、预计读完时间等统计；
3. **引用与笔记**：未选择文本时进入本书记录，选择文本后直接提供划线、引用和写消息。

字体、主题和版式不再占据第一层。它们从一个低权重的“更多”入口或应用级设置进入“阅读偏好”，并保留键盘可达性。上一页和下一页优先使用页面点击区域、滚轮、方向键和 Page Up/Page Down，不为已经存在的基础动作长期占用工具栏。

这里学习的是微信读书的层级关系，不是移动端几何。Atha 是 Windows 阅读器，具体控件位置、鼠标悬停、键盘焦点和读屏语义仍需按桌面场景单独设计和验收。

## 自定义分层

| 层级 | 面向谁 | 用户看到什么 | 状态与范围 |
| --- | --- | --- | --- |
| Level 0 | 绝大多数用户 | 不出现设置提示；跟随系统明暗主题，使用 Atha 选定的默认字体、字号、行高、页边距和翻页方式 | 应用默认；打开书即可读 |
| Level 1 | 明确想调整阅读感受的用户 | “阅读偏好”只提供主题、字号、阅读密度和翻页方式；字体作为次级选择 | 默认作用于全部书，可恢复默认；修改即时预览并保持当前位置 |
| Level 2 | 想修书或深度折腾的用户 | “高级 → 自定义样式”，直接编辑或导入 CSS | 默认按书生效；可预览、启停、撤销和恢复默认，错误不阻止安全打开书籍 |

Level 1 不应复制微信读书的完整排版台。行距、页边距和段落留白可合并成“紧凑 / 标准 / 舒展”三档阅读密度，减少互相影响的参数；只有真实用户反馈证明三档不够时，才拆成独立滑杆。主题首选“跟随系统”，避免把亮度控制永久放进阅读器。

Level 2 的 CSS 只作用于书籍内容，不作用于应用壳；加载顺序保持“书源 CSS → Atha 阅读样式 → 用户样式”。用户样式不得突破现有书根、网络和资源边界，至少需要语法错误提示、单次禁用、全部恢复和安全模式。该方向与 [产品定义](../product/OVERVIEW.md) 及 [阅读内核](../architecture/READER-CORE.md) 已有的用户样式覆盖层一致。

不要在 UI 中显示“Level 0/1/2”，也不要让用户先选择身份。用户是否继续下钻，本身就是分层机制。

## 为什么现在不开放 JavaScript

Atha 当前明确禁止不可信书籍脚本，并把外部资源、导航和宿主能力限制在受控边界内。直接向 Level 2 增加 JavaScript，会同时引入 DOM 与性能破坏、无限循环、网络与本地数据权限、定位和引用失效、错误恢复以及脚本分享信任等问题。这不是 CSS 编辑器旁多放一个文本框，而是一套新的扩展安全模型。

因此当前停止在 CSS。若以后出现 CSS 无法表达且反复发生的真实需求，再研究独立的“用户脚本”能力：它应与书籍脚本区分，默认无网络、无文件、无后端 IPC，按书授权，有执行预算，并能在启动时一键禁用全部脚本恢复阅读。没有这种需求前不建设。

## 后续验证问题

进入 R3 具体设计前，只需验证以下假设：

1. 用户在一次阅读会话中实际反复打开的是目录、进度还是引用入口；
2. “紧凑 / 标准 / 舒展”能否覆盖 Level 1 的大部分版式需求；
3. 第一控制层只有三个带文字标签的入口时，鼠标、键盘和触摸是否都能快速返回正文；
4. CSS 覆盖后，位置恢复、内容裁切、公式和历史引用快照能否继续满足现有契约。

在这些问题有真实交互证据前，不增加更多设置、人格化推荐或自动排版规则。
